# 5 人多人联测计划（2026-08-13）

- **版本**：0.4.1-beta.9（`65943a4f`）
- **人数**：1 owner（你）+ 4 位受邀者
- **形态**：全员先一起加入，然后**分 4 条线并行跑**，最后收口
- **节奏**：Phase -1 你自己先做（开测前一天）→ 约 100 分钟同步联测 → 3 天异步 dogfood

**不测**：多人同会话 / 多 agent 群聊；单人主链路（已有 e2e 护栏）；Windows；性能压测。

> 排期假设：你列的 4 条线一共 6 个人位，实际只有 4 个人，所以 **线 C 和线 D 由同一对 2 人先后跑**。
> 如果本意是 6 个人，告诉我改回去。另外你的编号从 1 跳到 3，缺的那条补进来我再加一节。

## 一、四条测试线

| 线 | 人数 | 谁 | 内容 | 机器/账号要求 |
|---|:---:|---|---|---|
| **A** | 1 | 受邀者 1 | 定时任务 + 企微 + SeaTalk | 能连企微/SeaTalk 的机器，最好也有手机 |
| **B** | 1 | 受邀者 2 | 控制浏览器 + 内置 MCP | **全新机器 + 全新账号，从没装过** |
| **C** | 2 | 受邀者 3、4 | skills / env 共享 | 其中 1 人**本来就有自己的团队/org** |
| **D** | 2 | 同上 2 人 | MCP + knowledge 共享 | 同上，跑完 C 接着跑 D |

**为什么这么摊机器要求**——每条线顺便扛一个只在特定机器状态下才暴露的风险：

- 线 B 的人给全新机器：首启路径（#895）只有"从没装过"才测得到，装过一次再也复现不了。**别让人帮他配环境**，坑就藏在没人指导里。
- 线 C 里安排一个已有团队的人：验 #893 停掉静默 team fallback，以及跨 org 团队在选择器里可见但被 RLS 挡住的老问题。
- 你自己（owner）扛 #899 家目录 v2 的升级路径，见 Phase -1。

## 二、全程盯着的两件事（不属于任何一条线）

不安排时间点，谁在任何时候看到都立刻记：

| # | 盯什么 | 为什么 |
|---|---|---|
| W1 | **有没有人卡在 loading 转圈** | Sentry 第一名：`loadFirstPage` 里两个没有 try/catch 的 local_cache await，抛了就永久转圈。转圈超过 10 秒就记，哪怕最后转出来了 |
| W2 | **有没有静默失败** | 界面看起来正常但事情没发生——skill 显示已装其实没到、凭证显示已存其实没落盘、knowledge 文件同步了但检索不到。比报错难查，也比报错值钱 |

## 三、Phase -1：你自己先做（开测前一天，别占用 4 个人的时间）

### 停止线 1 — 升级路径

`docs/amuxd-home-directory.md` 写得很直白：新版**不迁移旧数据**，首启按固定清单删掉 v1 留下的东西（根目录散文件、`history/`、`mcp-configs/`、`team-secrets/`、`bin/`、旧的 `<config_dir>/amux/`），**然后需要重新 onboard 一次**。理由是旧 `backend.toml` 的 refresh_token 还能换 access token、`daemon.toml` 里 channel bot token 和 cursor api_key 是明文。

| # | 验什么 | 预期 |
|---|---|---|
| U1 | 升级前先 `cp -a ~/.amuxd ~/.amuxd.bak` | 有回滚路径再动手 |
| U2 | 升上来后会话历史还在吗 | 消息在服务端，应当还在 |
| U3 | 需要重新 onboard 吗 | **是**，这是设计不是 bug——但引导流程要走得通，不是白屏 |
| U4 | channels 凭证（企微 bot secret）还在吗 | **不在，要重录**。确认重录后能存住。**线 A 直接依赖这条** |
| U5 | 个人密钥（`~/.teamclu/`）还在吗 | **在**，桌面家目录不受影响 |
| U6 | `<workspace>/teamclu-team` 软链还指得对吗 | 指向 `~/.amuxd/teams/<id>/shared/teamclu-team` |

这条不通就别开联测——4 个人里只要有一个是升级上来的，会全场卡在这。

### 停止线 2 — share mode 一次性锁定

`POST /v1/teams/:id/share-mode` 是**一次性锁定**，重复锁返回 409。全场只有这一个决定改不回来，而且**线 C、线 D 全部建立在它之上**。

→ 先用一个"演练团队"把 oss / managed_git / custom_git 的开通流程走一遍，确认你要的那个模式真能通，正式团队再锁。锁错了只能重建团队，4 个人得重新加入一遍。

### 其余开测前检查

- [ ] 5 个人**同一个 build、同一个 brand**。品牌构建只认自己的 scheme（#871），`amux://invite?token=…` 在别的 brand 包里点不开
- [ ] team LLM provider 已 provision，额度够 5 人 × 2 小时。**本机那个 bailian key 已过期、minimax 额度打满，是故意留着测失败路径的 fixture，别拿它当联测 provider**
- [ ] 线 A 的企微 / SeaTalk 通道提前连好，绿点确认（凭证按 U4 重录过）
- [ ] Sentry 在收 4 位受邀者的上报
- [ ] 4 个人的账号邮箱都是 **verified email**——`inviteEmail` 那条路靠 verified email 匹配才会在 pending 列表里出现
- [ ] 建好收 bug 的地方（模板见第七节）

## 四、Phase 0：全员加入（T+0 ~ T+20）P0 —— 唯一必须串行的一段

**每个人独立操作，不许互相看屏幕。** 加入流程的坑全在"第一次、没人教"里。

| # | 谁 | 步骤 | 预期 |
|---|---|---|---|
| J1 | 线 B 的人 | 收 `amux://invite?token=…` deeplink，点开加入 | 唤起 app → 落到团队里；**冷启动状态下点 deeplink 也要能进**（#880） |
| J2 | 线 C 的人之一 | 不发 token，只用 `inviteEmail`：登录后自己去看待处理邀请 | pending 邀请自动出现，无需任何链接送达 |
| J3 | 线 C 里有自己团队的那位 | 用**已有团队**的账号加入 | 团队选择器里两个团队都在；切过去后会话/成员/skill 全跟着切；**不出现静默 fallback 到别的团队**（#893） |
| J4 | 任意 | 拿一个已被用掉的 token 再 claim 一次 | 明确报错文案，不是白屏/无反应 |
| J5 | O | 线 A 的人邀为 admin，其余为 member | 成员列表角色显示正确 |
| J6 | 一位 member | 用 member 身份翻设置 | 看不到 owner-only 的项（LLM provider、share mode 等） |

**已知会撞的两个坑，提前认领：**

- 403 `upgrade_required` = 该账号还在共享默认 org（solo-only），member 邀请要求账号升级到自己的 org。谁撞到，记下是哪个账号状态。
- 团队选择器里可能出现**跨 org 的团队**：看得见，点进去被 RLS 全挡。服务端活跃 org 与客户端当前团队互不校验。

**验收**：5 个人都在成员列表里、角色正确、都能进同一个团队。做不到就停在这里排查，**不要放人去跑各自的线**。

## 五、Phase 1：四条线并行（T+20 ~ T+80）

四个人各跑各的，互不等待。你（owner）在中间做"发布方"——线 C / D 需要你先发东西他们才有得收。

### 线 A（1 人）：定时任务 + 企微 + SeaTalk

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| A1 | cron 基本盘 | 建一条 3 分钟后跑的任务 | 到点自动起会话、执行、结果留在记录里 |
| A2 | **cron 免审批** | 让该任务触发一个需权限的工具 | **默认 full access 直接跑过**。无人值守场景等审批就是跑不完——卡在弹窗就是 bug |
| A3 | cron 投企微 | 配置投递到企微群 | 群里收到，格式不乱 |
| A4 | cron 投 SeaTalk | 配置投递到 SeaTalk（#898 新加） | 同上。**这条是本轮第一次真机验 SeaTalk 投递** |
| A5 | 企微网关收发 | 群里 @ bot 派一次活 | 消息路由到 agent，回复回到群 |
| A6 | **凭证持久性** | 改一次 channel 配置 → 重启 daemon | 凭证还在，不用重填 |
| A7 | **多 bot 不串** | 配 2 个 bot，交替发 | 各回各的，密钥不错配 |
| A8 | 手机侧 | 在手机企微里 @ 一次 | 与桌面行为一致 |

> **A6 / A7 是本轮最该认真做的两条。** layout v2 的 ⑤-A 把 channels 凭证下沉进了 `secrets.enc`（按 bot_id 而非数组下标索引），架构文档自己写着"**⑤-A 未经真实网关联测**：wecom 回调、多 bot 轮换等只有单测覆盖，发布前需要一次真机验证"。这条线就是那次真机验证。

### 线 B（1 人，全新机器）：控制浏览器 + 内置 MCP

内置 MCP 在代码里是四个、不可删除：`playwright`、`chrome-control`、`autoui`、`teamclu-introspect`。内置技能两个：`macos-control`、`windows-control`。

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| B0 | **首启全流程**（顺带） | 全新机器第一次打开，自己走完 | 首启向导走得通，本机 agent 静默绑定成功（#895），**全程不用别人教** |
| B1 | 内置 MCP 列表 | 打开设置 → MCP | 四个都在、标为"内置"、**删不掉**（`inherentCannotDelete`） |
| B2 | 内置技能列表 | 打开设置 → 技能 | `macos-control` / `windows-control` 标为"内置"、删不掉；按平台只显示该显示的那个 |
| B3 | **浏览器控制主链路** | 让 agent 开个网页、点一下、取一段内容 | 真的驱动起浏览器并拿回结果，不是嘴上说做了 |
| B4 | **路由正确性** | 让 agent 做一件"开网页"的事 | 走浏览器工具，**不会误用 `macos-control`**——那个 SKILL.md 明写着 "NEVER invoke this skill for opening web pages" |
| B5 | 桌面控制 | 让 agent 操作一个本地 app（`autoui` + `macos-control`） | Probe → Route → Act 流程跑通；AX 树不全时降级到 Layer 2 而不是瞎点 |
| B6 | introspect | 触发 `archive_session`（#840） | 工具可用，会话被归档 |
| B7 | **权限审批** | 观察上面这些高风险工具触发时 | 弹审批弹窗，允许/拒绝都按预期；拒绝后 agent 不硬来 |
| B8 | 内置 vs 团队同名 | O 加一个与内置同名的团队 MCP | 有明确的优先级或冲突提示，不静默互相覆盖 |

### 线 C（2 人）：skills / env 共享

两人分工：先都当**接收方**（O 发布），再让其中一人当**发布方**、另一人收——顺便验 member 有没有发布权限。

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| C1 | **skill 下发时延** | O 从 ClawHub 装一个 skill | 两人各记一个秒数；要不要手动同步/重启？**两台机器不一样才是信息** |
| C2 | 版本跟随 | O 发布该 skill 新版本 | 成员端自动跟到 `latest_version`（#886），不用手动升 |
| C3 | 本地改动保护 | 其中一人本地改了同一个 skill 再保存 | 保存后立刻 re-check（#892），本地改动不被静默覆盖 |
| C4 | **skill 真能用** | 收到的人在会话里实际调用该 skill | 真的执行，不只是列表里出现 |
| C5 | env 下发 | O 写一个团队 env 变量 | 两人的 agent 读得到 |
| C6 | **env 不泄明文** | 成员端去翻设置里的那个 env | 看不到明文值 |
| C7 | 成员发布权限 | 一位 member 尝试发布 skill / 改团队 env | 按设计允许或拒绝——**关键是行为一致且有提示**，不是静默失败 |
| C8 | 断开重连后补齐 | 一人关 app 5 分钟再开 | 期间 O 发的 skill / env 补齐，不需要手动刷新 |
| C9 | 删除传播 | O 删掉一个已下发的 skill | 两人那边跟着消失，不留幽灵条目 |

### 线 D（同上 2 人，跑完 C 接着跑）：MCP + knowledge 共享

| # | 用例 | 步骤 | 预期 |
|---|---|---|---|
| D1 | team MCP 下发 | O 配一个团队 MCP server | 两人那边出现，记时延 |
| D2 | **team MCP 真能调** | 两人各自让 agent 调用该 MCP 的工具 | **真的调用得到**，不只是列表里出现。#894 把它收敛成所有 runtime 读同一个文件，这条验的就是那个收敛 |
| D3 | MCP 凭证 | 该 MCP 需要 key 时 | key 从团队 env 拿得到，成员端不见明文 |
| D4 | knowledge 文件同步 | O 往 `knowledge/` 放几篇文档（含中文、含大文件） | 两人那边文件到位 |
| D5 | **knowledge 真能检索** | 两人各自让 agent 查一个只有那批文档里才有的事实 | **答得出来**。文件同步过去 ≠ 索引建好了——这是本线最可能出问题的一条 |
| D6 | 索引在哪建 | 观察 D5 是否需要等待/手动触发 | 记录现象：是自动建索引，还是要手动点一下 |
| D7 | knowledge 更新 | O 改一篇已同步的文档 | 两人那边内容更新，**检索结果跟着变**，不是拿旧内容回答 |
| D8 | knowledge 删除 | O 删掉一篇 | 文件消失，**索引里也查不到了** |

## 六、Phase 2：收口（T+80 ~ T+100）P2，时间不够可砍

四条线跑完聚一下，做几件跨线的事：

| # | 用例 | 预期 |
|---|---|---|
| R1 | O 把线 C 的一个人移出团队 | 立刻失去访问；已下发的 skill / MCP / knowledge 一并失效，不是留在本地继续能用 |
| R2 | admin（线 A 的人）邀请/移除成员；member 尝试同样操作 | admin 可以，member 被拒且提示明确 |
| R3 | 有人登出再登回 | 状态恢复，不需要重新 onboard |
| R4 | 4 个人各报一次 W1 / W2 的观察 | 汇总转圈和静默失败的现场 |

## 八、通过门槛

| 级别 | 内容 | 要求 |
|---|---|---|
| **P0，必须全绿** | Phase 0 全部 + A2 + A6 + B3 + C1 + C4 + D2 + D5 | 不绿不能对外放 |
| **P1，允许带缺陷但必须记录** | 四条线其余全部 | 每条都要有结论，不能"没测到" |
| **P2，可延后** | Phase 2 收口 | 时间不够可以砍 |

P0 那几条挑的是"**东西到了**且**真的能用**"：`C1`/`C4` 是 skill，`D2` 是 MCP，`D5` 是 knowledge，`B3` 是浏览器控制，`A2`/`A6` 是无人值守链路。

另外四条硬性输出，联测结束当天就要有：

1. **升级路径结论** — 从 beta.8 升上来是不是必须重新 onboard、要重录哪些东西 → 写进 release note，否则用户以为炸了
2. **网关真机结论** — ⑤-A 那句"未经真实网关联测"能不能划掉（线 A 的 A6/A7）
3. **资产下发时延** — C1 / D1 / D4 在两台机器上各自的秒数，以及有没有哪台需要手动介入
4. **knowledge 索引结论** — D5/D6：文件同步过去之后，索引是自动建还是要人点
